## Module-level shortcuts

The everyday lifecycle, instrumentation, and state-query calls are importable
from the package root, so the common case needs no class name:

```python
import scope_profiler as sp

with sp.session(file_path="run.h5", return_results=True) as run:
    with sp.region("solve"):
        solve()

results = run.results
```

`sp.setup`, `sp.finalize`, `sp.session`, `sp.region`, `sp.profile`,
`sp.is_active`, `sp.is_configured`, `sp.registered_regions`, and
`sp.recorded_regions` *are* the corresponding `ProfileManager` class methods
rather than wrappers around them, and act on the same process-wide default
manager. Use `ProfileManager` directly for independent manager instances.

### Library instrumentation that is off by default

A library registers an opt-in tag once with `sp.register_opt_in_tag("mylib")`
and passes `tags=("mylib",)` to `region`, `profile`, `define_region` or
`instrument`. Those regions stay disabled until a run enables the tag with
`setup(enable_tags=["mylib"])`, the `enable_tags` TOML setting,
`SCOPE_PROFILER_ENABLE_TAGS=mylib` or `scope-profiler run --enable-tag mylib`.
The registry is process-wide and shared by every manager.
`sp.opt_in_tags()` maps each registered tag to the regions known to carry it,
and `scope-profiler tags` lists the tags of the installed packages; a library
makes its tags discoverable there with a `scope_profiler.opt_in_tags` entry
point (see the [CLI reference](/scope-profiler/reference/cli/#scope-profiler-tags)).

Test suites reset the profiler between tests with `sp.reset()`, which keeps
the instrumentation (decorated functions and `define_region` definitions)
so that it records again after the next `setup()`.

## ProfileManager

The main entry point for all profiling operations. Class methods provide the
process-wide default manager, so the common case does not require an instance.
Create `ProfileManager()` instances when independent profiling sessions need
to coexist; each instance owns its configuration, regions, decorators, and
output.

## ProfilingOptions

The settings `setup()` and `session()` accept, as an object that can be built
away from the call site and reused across runs. It is also where each setting
is declared once: the keyword arguments of `setup()` are its fields.

Settings that share a prefix can be given as groups instead, which spell the
same thing without the prefix:

```python
from scope_profiler import HDF5Options, ProfilingOptions

options = ProfilingOptions(
    file_path="run.h5",
    hdf5=HDF5Options(compression="gzip", compression_level=4),
)
```

## Post-processing

Everything in this section is importable from the package root:

```python
from scope_profiler import (
    build_call_arrays,
    build_call_stack,

    read_h5_summary,
    read_json,
    read_profile,

    write_region_statistics_json,
```

All durations and timestamps exposed here are in **seconds**; the HDF5 file
stores nanoseconds.

### Call stack reconstruction

Regions record no call graph, so nesting is recovered from timestamp
containment. `ProfilingResults.call_stack()` is the usual entry point; the
functions below operate on its result and let you walk the reconstructed tree
when building your own nested visualisation.

<Autodoc name="scope_profiler.call_stack.build_call_stack" headingLevel={4} />
<Autodoc name="scope_profiler.call_stack.call_stack_roots" headingLevel={4} />
<Autodoc name="scope_profiler.call_stack.call_stack_children" headingLevel={4} />

#### Intervals must be properly nested, within a lane

Two calls recorded on one *lane* — one thread, or one asyncio task or greenlet
running on it — either nest completely or do not overlap at all. A call that
starts inside another on the same lane and ends after it raises `NestingError`
rather than being reconstructed under a guessed parent — there is no call
stack that describes it, and every consumer (flame chart, `.prof`, speedscope,
exclusive time) would otherwise have to invent one.

Calls on different lanes overlap freely and are reconstructed as separate
stacks. A run profiled with `track_threads` records a lane per call, which is
what makes that possible; without it a whole rank is one lane, so profiling
concurrent threads raises here instead. See [Threads, tasks and
coroutines](/scope-profiler/guide/concurrency/).

A stack of `with` blocks or decorated functions on one lane always satisfies
this. The other realistic way to violate it is a mismatched `sp_begin`/`sp_end`
pair in C or Fortran; see the [C](/scope-profiler/guide/c/) and
[Fortran](/scope-profiler/guide/fortran/) guides.

`finalize()` is deliberately more forgiving than the readers: a rank whose
intervals do not nest keeps its timings and loses only the call graph, with a
warning, rather than throwing away a run that has already finished computing.

<Autodoc name="scope_profiler.call_stack.NestingError" headingLevel={5} />

#### Reconstruction at scale

`build_call_stack` allocates a dict per call (~700 bytes), which is fine for
inspecting a run and not fine for a long one. `build_call_arrays` returns the
same reconstruction as numpy columns and is what the exporters and
`finalize()` use — a run with ten million events per rank reconstructs in a
couple of seconds instead of a couple of minutes.
